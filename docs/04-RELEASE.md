# 04 — Версии и релизы

## Схема версионирования

```
versionName = МАЖОР . МИНОР . НОМЕР_РЕЛИЗА        например  1.0.2
versionCode = номер сборки CI (github.run_number)  например  39
```

**Patch-компонента версии — это порядковый номер релиза.** Поэтому каждому
GitHub Release соответствует ровно одна версия, и наоборот:

| Релиз | Версия | Тег | Заголовок релиза |
|---:|---|---|---|
| #1 | 1.0.0 | `v1.0.0` | v1.0.0 — релиз #1 *(выпущен до введения схемы)* |
| #2 | 1.0.2 | `v1.0.2` | v1.0.2 — релиз #2 (сборка 39) |
| #3 | 1.0.3 | `v1.0.3` | v1.0.3 — релиз #3 (сборка 40) |

В приложении это видно в «Настройки → Обновления» и «Настройки → О приложении»:
`1.0.2 (релиз 2 · сборка 39)`.

Источники данных:

| Что | Где |
|---|---|
| База версии (`МАЖОР`, `МИНОР`), номер последнего релиза | [`version.properties`](../version.properties) |
| Вычисление следующего номера релиза | [`scripts/version.sh`](../scripts/version.sh) (по тегам `vX.Y.Z`) |
| Номер сборки (`versionCode`) | `github.run_number`, задаёт CI |
| Запись факта релиза в репозиторий | [`scripts/record_release.py`](../scripts/record_release.py) |

Номер релиза считается как `max(кол-во тегов vX.Y.Z, максимальный patch,
LAST_RELEASE) + 1`, т.е. он всегда растёт и никогда не переиспользуется.

## Как выпустить релиз

### Вариант 1 — мерж в `main` (основной)

Любой push в `main` публикует следующий релиз автоматически:

1. Смержите PR в `main`.
2. CI сам: вычислит номер релиза → соберёт и подпишет APK/AAB → создаст тег
   `vX.Y.N` и GitHub Release «vX.Y.N — релиз #N (сборка M)» → приложит
   `app-update.json` и `SHA256SUMS.txt` → допишет строку в таблицу «История
   релизов» в `CHANGELOG.md` и обновит `LAST_RELEASE` (коммит `chore(release): …
   [skip ci]`, новую сборку он не запускает).
3. Пользователи получат обновление автоматически — см. [05-AUTO-UPDATE.md](05-AUTO-UPDATE.md).

Текст примечаний к релизу = сообщение последнего коммита (+ автосгенерированный
GitHub список PR). Хотите внятные примечания — пишите внятный merge-commit.

### Вариант 2 — тег (релиз с конкретным номером)

Нужно выпустить версию с заданным номером (например, поднять минорную версию):

```bash
# меняем базу версии, если нужно: VERSION_MINOR=1 в version.properties
scripts/version.sh --mode next        # посмотреть, какой номер будет следующим
git tag -a v1.1.7 -m "Что нового:
- Новая функция A
- Исправление B"
git push origin v1.1.7
```

Номер релиза берётся из patch-компоненты тега (`v1.1.7` → релиз #7), текст
аннотации тега попадает в `releaseNotes` манифеста самообновления.

### Вариант 3 — ручной запуск (workflow_dispatch)

Actions → **Build & Release** → *Run workflow*:

- `version_name` пусто + «Опубликовать GitHub Release» выключено → обычная
  проверочная сборка с версией `X.Y.N-dev` (без релиза);
- «Опубликовать GitHub Release» включено → релиз со следующим номером;
- `version_name = 1.0.9` → релиз именно этой версии (релиз #9).

## Что не нужно делать руками

- **Не правьте `versionCode`** — его назначает CI (`run_number`), он только растёт.
- **Не правьте `LAST_RELEASE`** — его обновляет CI после публикации.
- **Не создавайте теги вида `auto-…`** — формат тегов только `vМАЖОР.МИНОР.PATCH`.
- Не переименовывайте `.github/workflows/android.yml` — сбросится `run_number`
  (см. [03-CI-CD.md](03-CI-CD.md#номера-сборок-build-numbers)).

## Проверка версии локально

```bash
scripts/version.sh --mode next          # следующий релиз: VERSION_NAME/RELEASE_NUMBER/TAG
scripts/version.sh --mode dev           # как будет помечена сборка ветки
./gradlew -q :app:printVersion          # что реально попадёт в APK
```

## Отмена / правка релиза

```bash
# удалить релиз и тег, затем выпустить заново (номер сборки будет уже новый)
gh release delete v1.0.3 --yes
git push origin :refs/tags/v1.0.3 && git tag -d v1.0.3
```

Номер релиза после удаления **не переиспользуется** автоматически: счётчик
опирается в том числе на `LAST_RELEASE` в `version.properties`. Если нужно
вернуть номер — поправьте `LAST_RELEASE` вручную в том же коммите.

## Чек-лист перед релизом

- [ ] Юнит-тесты зелёные (последний CI-запуск ветки прошёл).
- [ ] `CHANGELOG.md` — секция новой версии заполнена (таблицу «История релизов»
      CI допишет сам).
- [ ] Для тега: версия в теге = версии в changelog, patch = номеру релиза.
- [ ] (Опционально) APK из артефактов CI проверен на реальном устройстве.
